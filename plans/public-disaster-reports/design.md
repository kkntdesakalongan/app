# Public disaster reports

Design: Approved
Implementation: Current

## 1. Purpose and scope

Let the public submit disaster reports without an account. Let administrators manage the reports.

Included: public intake at `/disaster-reports/new`, optional image upload, and administrator list, detail, create, update, and delete pages.

Excluded: report publication, map pins, report locations, review states, and reporter contact details.

## 2. Functional requirements

| # | Capability | Users and access | Expected result |
|---|---|---|---|
| 1 | Submit a report | Public, without sign-in | Save a report with a required title and optional description and image. |
| 2 | Manage reports | Administrators with the required operation permission | List, view, create, edit, and delete reports through standard management pages. |
| 3 | Protect intake data | Public | Public users can submit but cannot list, read, edit, or delete saved reports or retrieve their images. |
| 4 | View an image | Authorized administrators | Show the saved image on report detail and allow replacement or removal during edit. |

## 3. Data and business rules

### Disaster report

| Field | Meaning | Rules |
|---|---|---|
| ID | Record identity | Generated by the server; cannot be edited. |
| Title | Short report name | Required; trim whitespace; reject an empty result. |
| Description | Additional information | Optional plain text; an empty value means no description. |
| Image | Supporting image | Optional; at most one image. Accept PNG, JPEG, or WebP up to 5 MB. Validate file type, signature, and size on the server. |
| Created at | Submission time | Set by the server; cannot be edited. |
| Updated at | Last change time | Set by the server after a saved change. |

Image access follows report access. Public upload authority is limited to intake images; it must not grant access to other assets. A failed upload must not save a report that references a missing image. Removing an image must not remove an asset used by another record.

Reports and map pins are separate records. A report does not create a pin.

Approved defaults: administrators can create reports, and report content remains private. No additional business fields are proposed.

## 4. User journeys and workflows

### Public submission

1. Open `/disaster-reports/new` in a public form shell.
2. Enter a title and, if needed, a description and one image.
3. Submit. Show confirmation after the save succeeds. Offer a clear action to start another report.

### Administrator management

1. Open the disaster reports navigation entry.
2. Use the standard list, detail, create, update, and delete flows.
3. Confirm deletion before the write. Refresh the list after a confirmed save or delete.

| Trigger or condition | Result | Next step |
|---|---|---|
| Invalid title or image | Show a field error and keep entered values. | Correct the value and submit. |
| Upload or save fails before a confirmed write | Show the error and keep the form values. | Retry the failed action. |
| Save succeeds but navigation fails | Keep the saved result. | Retry navigation without another write. |
| Access is denied | Show the access error; do not expose report data. | Return to an allowed page. |
